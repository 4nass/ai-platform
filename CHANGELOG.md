# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- CLI (`uv run ai-platform run "<request>"`) driving Claude Code as the active provider, plus a `--dry-run` flag that prints the planned workflow and task selection without invoking any workflow-task agent (`memory/adr/ADR-001-cli-dry-run-flag.md`).
- Multi-stage workflow engine: a task DAG (`config/workflow.yaml`) executed per-task in isolated git worktrees (`core/orchestrator/git_ops.py`), merged back with `--no-ff`, with a Task Decomposer role that prunes the plan per request.
- Context Engineering Layer: tree-sitter/section chunking, an embedded Qdrant vector index, and a git-history + PageRank dependency graph (`core/graph/builder.py`, combining AST imports, git co-changes, and doc mentions).
- Per-role artifact contracts (`core/orchestrator/contracts.py`): a post-hoc check on which files each role is allowed to touch, backstopping the CLI tool restrictions.
- Review gate: every run's diff is sent to a `reviewer` role, and its PASS/FAIL verdict gates completion (`core/orchestrator/review.py`).
- Run telemetry (`core/telemetry/store.py`): per-call and per-run cost/token accounting, config snapshots, and routing/context decision logs.
- Two working providers: `claude_code` (`claude -p`) and `codex_cli` (`codex exec --json`), both subprocess CLIs that edit files themselves. `anthropic_api` (Messages API, Pydantic-structured output) is implemented but unexercised — it needs an API key rather than a subscription.
- Provider routing (`core/orchestrator/router.py`): each role declares an ordered preference in `config/agents.yaml`, and the router skips a candidate only on measurable grounds — quota pressure, or a success rate below the floor on a large enough sample (`config/routing.yaml`). Every choice is recorded in the `routing_reason` column, and `ai-platform route` explains one without spending a token.
- Subscription quota accounting (`core/telemetry/quota.py`, `config/quota.yaml`): neither CLI reports a remaining balance, so declared budgets are compared against tokens actually recorded. `ai-platform quota` shows the pressure per provider.
- `ai-platform context` and `ai-platform route`: inspect the file selection and the provider choice without invoking an agent.
- `ai-platform history`: shows recent runs' cost, tokens, duration, and outcome from recorded telemetry.
- `--repo` flag on `run`, `context` and `history`: operate on any git repo, not just the ai-platform repo itself. The engine's own config/prompts/telemetry stay fixed at the install (`ENGINE_ROOT`), separate from the repo actually being modified (`target_root`) — `core/orchestrator/scheduler.run_task` and `core/orchestrator/supervisor.run` now take both explicitly.
- Per-target `.ai-platform.yml` declares the test command `core/orchestrator/test_runner.py` runs — `pytest -q` is only true for this repo, so a `--repo` target on another stack (npm, go, cargo, ...) provides its own. Absent entirely, tests are skipped and clearly labeled `SKIPPED`, rather than run against a command that doesn't apply.
- Bounded test/review correction loop: when tests fail or the review verdict is FAIL — and every DAG stage otherwise completed — a new `corrector` role gets the failure output for up to `max_correction_attempts` fix-and-recheck passes (`config/workflow.yaml`, default 1) before the run reports `needs attention` (`core/orchestrator/correction.py`, `prompts/corrector.md`).
- Model and reasoning effort are now routing dimensions, not just provider (`core/orchestrator/router.py`). A role declares ordered *execution profiles* (`{provider, model, effort}`) instead of bare provider names, and `profiles_by_complexity` can override the list per task class. The decomposer classifies each request as `routine`/`complex`/`critical` — a bounded, parser-validated choice — and that class selects which profile list applies; models themselves are never invented by an agent. `effort` is provider-neutral in config: adapters translate it to `claude --effort` or codex's `model_reasoning_effort`. Both gates now scope to the exact profile, so two profiles of the same provider are judged separately. Policy and rationale in [`docs/model-routing-policy.md`](docs/model-routing-policy.md).
- `ai-platform route --complexity` explains the choice for a given task class, with the resolved model/effort shown as its own column.
- **Durable asynchronous run lifecycle** (`core/jobs/`, issue #24): `ai-platform submit` persists a request *before* acknowledging it, returns a job id and starts a detached worker, so a caller can disconnect and reconnect later from another process. `status`, `jobs`, `cancel` and `work` read and drive that queue. Every state transition across `queued | running | waiting_approval | succeeded | failed | cancelled | interrupted` is validated against a transition table, timestamped and idempotent — reapplying a state is a no-op, and an illegal one raises rather than being recorded, since an audit trail that lies is worse than none. A `job_events` table keeps how a job reached its state, which is the only thing that can answer "why is this interrupted" after the process that interrupted it is gone. Kept in `jobs.sqlite`, separate from `telemetry.sqlite`: telemetry is append-only analytical memory where a row means *a run happened*, and every query over it (`recent_runs`, `run_totals`, `role_performance`, `provider_pressure`) assumes that — a queued or cancelled job is not a run, and mixing them would mean adding a state filter to all of them and getting it wrong somewhere. `jobs.run_id` links the two once execution starts. No new dependency; SQLite throughout.
- **Crash recovery.** A running job heartbeats from a background thread — a single provider call can take minutes, and a run is at its most alive exactly when it has nothing to report, so beating only at stage boundaries would make the longest, most normal part of a run look like a crash. Reconciliation (run on every read path, because a restart is exactly when nobody is around to run a repair command) marks jobs whose heartbeat went stale as **`interrupted`** rather than `failed`, keeping `base_ref`, `base_sha`, branch, stage, attempt and the integration-worktree path so committed work stays inspectable rather than orphaned. Staleness is judged on heartbeat age, not a liveness check on `worker_pid`: pids are only meaningful on the host that issued them and get reused. Verified by killing a real worker mid-run — the job landed `interrupted` with its branch carrying the completed stage's commit, and the CLI pointed at the worktree still on disk. Resuming mid-DAG needs per-stage checkpointing that doesn't exist yet and is not claimed.
- **A killed run left the target's git hooks disabled forever.** `disable_hooks` rewrites the repository-wide `core.hooksPath` and restores it in a `finally` — and a `finally` only runs if the process lives to run it. Killing a worker mid-run (now a first-class case) left the target pointing at the engine's neutralization directory permanently, silently disabling the user's own hooks in their repository. Surfaced by SIGKILLing a real worker while verifying crash recovery, and confirmed on the damaged repo afterwards. The previous value is now written to the repo's own config before the swap, so `git_ops.restore_hooks` can put it back exactly — including a custom path, which an in-memory-only save loses. Reconciliation repairs it when it learns a run died. It only ever reverses the engine's *own* neutralization: if `core.hooksPath` now points somewhere else, someone set it deliberately after the crash and that is not the engine's to overwrite.
- `supervisor.run` takes an optional `progress` callback, so a run reports `base_sha`, branch, integration worktree, in-flight stages and correction attempt as it reaches them. A bare callable rather than a job-store handle: the supervisor should not know a durable queue exists. Guarded so a failing observer can never fail the run it is describing.
- `--dirty-policy` on `run`: `head` (default) works on the base commit alone and reports how many local modifications it left out; `reject` refuses to start on a dirty target; `snapshot` is declared but fails loudly as unimplemented, rather than silently behaving like `head` and recording `snapshot` in the telemetry. Every run records `dirty_policy`, `source_dirty` and the excluded count in its metadata — a run whose source was dirty is not reproducible from `base_sha` alone, and the excluded edits explain a result the commit doesn't.
- `.gitattributes` normalizes the repo to LF. An agent-driven CLI writing CRLF under WSL2 had turned a no-op into a 19-file, whole-file diff — unreviewable, and enough to make the review gate judge noise instead of the change.

### Changed

- Each run now gets its own **integration worktree** rather than checking `engine/<slug>` out in the target repo. A run used to switch the user's HEAD out from under them, leave them on the engine branch afterwards, and make two concurrent runs impossible since both wanted the same checkout. Every merge, correction commit, test run and diff now happens in that worktree (`git_ops.create_integration_worktree`); the target's own tree is only ever read. Removed on success (the branch is the deliverable), kept with its path printed on failure. Consequently a dirty target tree is no longer a hard precondition — `ensure_clean_worktree` is gone, replaced by `git_ops.local_modifications`, and a dirty tree is reported rather than refused (see the `--dirty-policy` entry). One knock-on fixed at the same time: `core/graph/builder.load_or_build` justified its HEAD-only cache key with "callers only reach this after ensure_clean_worktree", which stopped being true — it now declines to *write* a cache built from a dirty tree, scoped to changes outside `.ai-platform/` so the engine's own generated artifacts don't count (the cache file itself otherwise made the tree permanently dirty in a target that doesn't gitignore it).
- The default architecture and security profiles are calibrated for a Pro subscription: Codex is preferred at every complexity, Claude Sonnet is the routine/complex fallback, and Claude Opus/high is reserved for critical fallback. `ultracode` remains adapter-supported but is not selected automatically.
- Context selection now scores and gates candidates instead of injecting whatever retrieval returned: vector hits require a similarity floor, graph expansion is gated by lift (personalized vs. background PageRank), and every candidate's keep/drop decision is recorded (`core/context/selection.py`).
- Rendered context (not just file paths) is now actually sent to providers; each adapter declares `READS_FILES` to choose between full content and a ranked pointer map.
- Token accounting sums cached and uncached input tokens instead of reporting only the uncached remainder, so reported cost reflects the full prompt (`providers/anthropic_api/adapter.py`, `core/orchestrator/supervisor.py`).
- Reporting leads with tokens, duration and outcome rather than dollars. With two flat-rate subscriptions a per-call price measures nothing actionable; cost is still recorded where a provider volunteers one, but nothing decides on it.
- `providers/base.TokenUsage` now states the platform's token convention explicitly, and each adapter converts into it. Anthropic reports the cached count *disjoint* from the input count; OpenAI reports it as a *subset*. Summing both shapes the same way would have reported 25,002 tokens for a 13,994-token Codex prompt.
- Documentation's artifact contract broadened from `README.md`/`memory/*.md` to any `*.md` file, after a real run needed to create `CONTRIBUTING.md` at the repo root (`core/orchestrator/contracts.py`).
- `tests` role now prefers `codex_cli` over `claude_code` (`config/agents.yaml`).
- `telemetry.sqlite` is now shared across every `--repo` target instead of living inside whichever repo happened to be operated on: quota is a subscription resource, not a per-project one, so routing/quota pressure has to aggregate across all of them. Each run records which target it touched (`runs.target_repo`, backfilled on migration for pre-existing rows); `ai-platform history` scopes to the resolved `--repo` by default.
- The vector store and dependency graph cache moved from `vector/qdrant_db` / `vector/graph.pkl` to `.ai-platform/vector/qdrant_db` / `.ai-platform/graph.pkl`, always under the target repo being indexed — a single, target-scoped rule that also holds up for an external `--repo` target, which never had a `vector/` directory of its own.

### Fixed

- `Plan.prune()` now bridges dependencies through pruned nodes instead of dropping them.
- Any exception in a DAG worker crashed the whole run and stranded its git worktree (issue #1): `_run_stage_in_worktree` created the worktree before anything that could raise but caught only `git.GitCommandError`, so a `ConfigError` from an undefined role — or a provider raising instead of returning a failed result — propagated through `future.result()` on the main thread. The worker body is now fully guarded and returns a failed `StageResult` with its worktree path so cleanup still happens, `future.result()` has a backstop for a bug in that guarantee itself, and worktree removal is best-effort rather than fatal. Verified against the original reproduction: previously crashed with one leaked worktree, now the bad stage fails alone, an independent sibling still completes, and nothing leaks. Also added `tests/conftest.py` — `create_worktree` uses `tempfile.mkdtemp()` deliberately outside the repo, which is also outside anything pytest's `tmp_path` cleanup reaches; one suite run left 5 directories behind and 354 had accumulated.
- `--dry-run` no longer requires a clean worktree.
- Routing reads telemetry from the main repo rather than the task's throwaway git worktree. It had been deciding from an empty database — every DAG stage cold-starting forever — and leaving a stray `telemetry.sqlite` inside the worktree for that stage's own commit to pick up (`core/orchestrator/scheduler.py`).
- Task branches are uniquified like run branches. A stage that failed kept its branch on purpose, so its partial work stays inspectable, but the next run of the same request then died inside `git worktree add` before reaching its provider (`core/orchestrator/git_ops.py`). The failure path now also says where that partial work went.
- A failed provider call records why it failed. The table previously held `success = 0` and nothing else, which measures a failure rate without explaining one; the message is queryable via `json_extract(metadata, '$.error')`.

### Security

- **Privilege escalation: a run could grant itself permissions by rewriting `.ai-platform.yml` mid-run.** That file decides whether the test command is sandboxed and what it is, and roles without an artifact contract (`backend`, `frontend`, `tests`, `corrector`) may write any tracked file. The final test run re-read it off the integration worktree, so a stage could commit `test_sandbox: false` with an arbitrary `test_command` and have the engine honour it — issue #4's sandbox disabled by exactly the code it was meant to contain, while the run still reported `done`. Demonstrated end to end before the fix. The policy is now read once from the run's **base commit** into a frozen `TargetConfig` (`core/orchestrator/target_config.py`) and never re-read; an edit on the produced branch is a reviewable change that applies to the *next* run.
- Verification moved into a disposable worktree, and gitignored writes are now classified rather than uniformly rejected. The ignored-write check from issue #2 treated every gitignored path as hostile, so a stage that ran the project's tests was rejected and its work discarded because pytest created `.pytest_cache/` — found by a real run. A project now declares `allowed_ephemeral_writes` (validated: absolute paths, `..`, anything under `.git/`, and catch-alls are refused, so it can't quietly disable the check); those are reported, anything undeclared still blocks. The test command additionally runs in a throwaway checkout of the run branch, deleted straight after, so its caches never reach the branch under review nor get attributed to the corrector. Ignored-write baselines are taken per actor rather than once per run.
- Mutating runs are serialized per repository (`git_ops.exclusive_run_lock`): `disable_hooks` rewrites repository-wide `core.hooksPath`, which two concurrent runs would race to restore. A second run now fails fast with an explanation instead of blocking silently. The lock is taken **before the run's first mutating operation** — the first version acquired it once the integration worktree already existed, so the run that got refused had already pruned, created a branch and checked out a worktree. Order is now lock → prune → capture `base_sha` → integration worktree → execute → cleanup → release, and `disable_hooks` sits inside the lock too, so it also covers worktree creation.
- **The context injected into a run is built from the run's own integration worktree, not from the user's checkout.** A run edits a checkout of `base_sha`, but file content, chunk excerpts and project memory were all read off `target_root` — so an uncommitted edit could describe code that did not exist in what the agent was editing, and an untracked file could be injected by a path the agent cannot open. Omitting the git diff would not have been enough on its own; the whole source has to move. `ContextManager` now separates the tree it reads from the tree it stores its index in (`storage_root`), so the index still lives in the project rather than in a directory the run deletes — which also keeps `commit_all`'s `git add -A` from sweeping `.ai-platform/` onto the branch in a target that doesn't gitignore it. Regression-tested in both directions: a marker present only in a local modification reaches neither the prompt nor the worktree, an untracked memory doc (loaded ungated, so its absence is a statement about which tree was read) is not injected, what the agents see is byte-identical to `base_sha`, and the user's checkout is unchanged down to its `git status`.
- Review-gate bypass: `parse_verdict()` matched the first `VERDICT:` occurrence anywhere in the reviewer's response, including one quoted from the diff under review; now anchored to the last line-start match, and fails closed on a malformed verdict (`core/orchestrator/review.py`).
- Same first-match parsing flaw in the Task Decomposer, where the prompt's own example could outrank the real decision.
- Path traversal in the Anthropic API provider: model-supplied file paths could escape the repo via `../` traversal, an absolute path, or a symlink; writes are now resolved and validated against the repo root up front, for the whole plan, before anything is written (`providers/anthropic_api/adapter.py`).
- `pickle.load()` on the knowledge-graph cache was an arbitrary-code-execution sink: unpickling attacker-controlled bytes at a gitignored path (invisible to `commit_all`/`contracts.violations()`/the reviewer's diff) runs in the parent process, outside any agent sandbox. The cache is now JSON (`.ai-platform/graph.json`, renamed from `.ai-platform/graph.pkl`) — every node/edge attribute was already a plain str/int/float, so nothing was lost. Verified with a real malicious payload: the same `os.system` pickle that used to execute now just gets rebuilt as a fresh cache (`core/graph/builder.py`).
- Agent-written tests used to run before any review verdict exists, with the invoking user's full, unsandboxed privileges (issue #4) — inherent to running the target's own suite as the verification step, but the execution itself had no isolation at all. `core/orchestrator/test_runner.py` now runs the declared `test_command` inside a [bubblewrap](https://github.com/containers/bubblewrap) sandbox by default when `bwrap` is installed: the host filesystem stays read-only (so the command's own toolchain keeps resolving — there's no per-target container image to know what a repo needs), the target repo is bound read-write, and every namespace is unshared, cutting network access entirely. New `.ai-platform.yml` keys: `test_sandbox` (default `true`), `sandbox_cache_dirs` (default `["~/.cache"]`, extra read-write binds a toolchain's cache needs), `test_env`. Missing `bwrap` degrades to unsandboxed with a loud warning rather than failing or silently downgrading. Verified against the real binary, not mocked: a write attempted outside the repo raises inside the sandboxed process and never lands on the host filesystem, a network connection attempt fails with "Network is unreachable", and a write inside the repo still succeeds normally — caught and fixed two real bugs building this (a relative `repo_root` silently broke `--bind`/`--chdir` as "execvp uv: No such file or directory"; an early draft of the negative-control test planted its canary file under `/tmp`, which the sandbox deliberately keeps fully writable as scratch space, so the write "succeeding" proved nothing).
- Prompt injection via repo content or an upstream agent (issue #5): every stage's summary became the next stage's instructions verbatim, and file excerpts, memory docs, diffs and test output were all embedded raw. `core/untrusted.py` now wraps each of those with a per-call random-nonce delimiter and defangs the engine's control lines inside them, applied at all four prompt-building sites (`scheduler.build_stage_description`, `review.build_description`, `correction.build_description`, `SelectedContext.render`/`render_pointers`), with a matching provenance rule added to all nine role prompts. The two halves are deliberately not equivalent and the code says so: indenting `VERDICT:`/`TASKS:`/`COMPLEXITY:` is *mechanical* (the parsers are line-anchored, so it deterministically stops embedded content from carrying a real decision — verified against the real parsers, where an unmitigated smuggled `VERDICT: PASS` parses as a genuine pass and the wrapped one does not), while the delimiters themselves are *advisory* prompt engineering that a persuasive payload can still argue past. Not a security boundary; the containment for a steered agent remains tool restrictions, contracts, the test sandbox, and no auto-merge. A real reviewer call against a diff that both smuggled a passing verdict and argued for approval did resist, reporting the injection as a finding and returning `VERDICT: FAIL` — evidence, not a guarantee. Fixed one real bug found while wiring it: the fixed provenance note landed *inside* the per-file character budget rather than being counted as overhead, silently costing ~380 chars of selected-file allowance.
- Contract check and review gate were blind to gitignored paths and `.git/`: both derive from `commit_all`'s tracked-file diff, so a write to either was invisible regardless of role — including a hook planted in `.git/hooks/`, which is shared across every worktree of a repo (not per-worktree) and survives a task worktree's removal to fire on this same run's own later git operations. Fixed two ways: `git_ops.ignored_writes()` treats any gitignored write as a violation (marks the stage `violated`, same as a contract breach — its worktree is discarded, never merged; the corrector's own writes are checked the same way, stopping the correction loop outright since there's no worktree to discard there), and `git_ops.disable_hooks()` redirects `core.hooksPath` to an empty directory for the run's whole write-capable window, restored unconditionally after. Verified against a hook planted at the real `.git/hooks/pre-commit` path (not the redirected one) while protected, and confirmed the same hook fires normally again once protection is lifted.
